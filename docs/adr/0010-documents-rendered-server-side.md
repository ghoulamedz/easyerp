# Documents are rendered and archived on the server

PDFs are generated by the API, stored immutably alongside the document, and served as the archival artifact. The legacy app generated every document in the browser with `dart:html`, which guaranteed nothing about what a customer actually received or kept — its receipts even printed ordered rather than received quantities, and one template numbered every quote `DEV-001`. Server-side rendering also means a document looks the same to every user, in every language, forever, and that the numbering is the same numbering that appears on the page.

## Amendment: two copies, and the browser that renders them

The decision above says the artifact is a PDF the server renders. That held while the only renderer was a browser the API launched. It does not hold on a serverless host, which has no browser binary and no way to launch one, and the failure was not graceful: opening a document's paper raised an untyped error that a user could only read as "the request could not be completed", and every issued document on that host had a paper nobody could print.

The amendment splits the artifact in two, because they are two different claims:

- **The print copy is HTML**, rendered at issue and filed beside the PDF. It is what Print serves, and the visitor's own browser rasterises it. Every host can produce it — the template carries its own `@page { size: A4 }` stylesheet and needs no subresources — so "issued but not printable" stops being a state a deployment can reach. `GET <paper>/:id/print` serves those filed bytes; it never re-renders, for the same reason the PDF never did.
- **The PDF stays the archival artifact** and is filed only where the host has a rendering browser, decided by a capability probe (`isPdfRendererAvailable`) rather than by asking which platform this is. A host that cannot launch a browser files the HTML alone, records `printPath` without `archivePath`, and answers `ARCHIVE_UNAVAILABLE` for the PDF — the typed answer, not the 500.

Two consequences are deliberate. Print output is the *filed* HTML, so a document filed last year prints as it was filed; and Download on a host with no PDF is not a dead button — the interface says so and offers the print dialog, whose "Save as PDF" produces the same paper.

Nothing here weakens the immutability claim. Both copies are written once under the document number and refused on re-write, and the row records each one's sha256.

Where the bytes live is deployment configuration: a directory named by `DOCUMENT_ARCHIVE_ROOT` on a VPS, or Vercel Blob when `BLOB_READ_WRITE_TOKEN` is set, because a serverless filesystem is not durable. The choice is made once in the composition root; no service knows which backend it is talking to.
